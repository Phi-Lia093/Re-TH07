# `.std` 关卡数据的正式加载器

> 来源：`std_load_stage`（`FUN_00407610`, 42 行）。
>
> **补上了 `.std` 格式从第 10 轮起缺失的运行时部分。**
> 注意：前几轮误以为 `msg` 播放器读 `.std`，那已被否定；
> **这里才是 `stage*.std` 的真正加载器。**

---

## 1. 文件头结构（由加载逻辑确定）

```c
buf = res_load(path, 0);

count_a    = *(short *)(buf + 0);      // +0x00  u16
count_b    = *(short *)(buf + 2);      // +0x02  u16
offset_a   = *(int   *)(buf + 4) + buf;  // +0x04  u32，转绝对
offset_b   = *(int   *)(buf + 8) + buf;  // +0x08  u32，转绝对
obj_table  = buf + 0x490;              // 固定的对象指针表
```

### 1.1 与早期逆向的对照

早期（`docs/10`）从文件字节推出：

```
u16 unknown0, u16 unknown1, u32 offsetA, u32 offsetB
```

现在确认：

| 偏移 | 字段 | 用途 |
|------|------|------|
| `+0x00` | `count_a` | **对象数**（用于分配 `count_a × 0x24c`） |
| `+0x02` | `count_b` | **条目数** |
| `+0x04` | `offset_a` | 区段 A 起点 |
| `+0x08` | `offset_b` | 区段 B 起点 |
| **`+0x490`** | **对象指针表** | `count_a` 个 4 字节相对偏移 |

### 1.2 实测数据对照

```
stage1.std: count_a = 2, count_b = 19, offsetA = 1772, offsetB = 2732
```

- `count_a = 2` → 分配 **2 个** AnmInstance（`2 × 0x24c`）
- `count_b = 19` → 19 个条目
- `0x490 = 1168` → 指针表位置

### 1.3 全 8 关实测（**已验证**）

| 文件 | count_a | count_b | 指针表首项 | 文件大小 |
|------|---------|---------|-----------|---------|
| stage1 | **2** | 19 | 1176 | 3552 |
| stage2 | **8** | 35 | 1200 | 4388 |
| stage3 | **5** | 5 | 1188 | 3836 |
| stage4 | **4** | 10 | 1184 | 5920 |
| stage5 | **8** | 29 | 1200 | 5676 |
| stage6 | **2** | 4 | 1176 | 3144 |
| stage7 | **8** | 30 | 1200 | 5744 |
| stage8 | **8** | 30 | 1200 | 5744 |

**指针表首项恒在 1176–1200 之间**，与 `0x490 = 1168` 起点吻合
（表头之后紧跟数据，偏移约 8–32 字节）。

`count_a` 取值 2–8，全部指针均落在文件范围内 —— **结构完全自洽**。

## 2. 内存布局

```c
// 1. 分配对象数组
obj_array = malloc(count_a * 0x24c);      // AnmInstance 数组

// 2. 重定位对象指针表（+0x490 处）
for (i = 0; i < count_a; i++)
    table[i] += buf;                       // 相对 → 绝对

// 3. 重定位 offsetA / offsetB
offset_a = buf + *(u32*)(buf + 4);
offset_b = buf + *(u32*)(buf + 8);
```

### 2.1 `0x490` 这个常量

**对象指针表固定在 `+0x490`（1168 字节）处。**

这意味着文件头是**固定长度**的，而不是变长结构：

```
+0x000  count_a (u16)
+0x002  count_b (u16)
+0x004  offsetA (u32)
+0x008  offsetB (u32)
+0x00C  ...  填充/其他数据 ...
+0x490  对象指针表 [count_a × u32]     ← 相对偏移
        ...  区段 A / 区段 B
```

## 3. 区段 A 才是渲染数据（**修正**）

> **重要修正**：上一轮我写「区段 B 是渲染数据」，弄反了。
> 核对字段使用：`[299]`（offsetA）被读取，`[300]`（offsetB）**只赋值从不读取**。
> **真正被渲染的是区段 A。**

### 3.1 区段 A 记录结构（**已完全解出**）

```
每条 16 字节：
  +0x00  short  对象索引（指向 0x490 指针表）
  +0x02  short  填充
  +0x04  float  X
  +0x08  float  Y
  +0x0C  float  Z
```

### 3.2 stage1 实测

```
区段 A: 0x6ec .. 0xaac = 960 字节 = 60 条记录

rec0: idx=0  (-192.0, 6600.0, 0.0)
rec1: idx=1  (-192.0, 6600.0, 0.0)
rec2: idx=0  (-192.0, 6344.0, 0.0)     ← Y 递减 256
```

**这与第 10 轮从原始字节逆向出的结论完全一致**：
「`f1` 值以 256 为步长递减，`f0` 恒为 -192」。
两条独立路径互相印证。

### 3.3 渲染流程（std_render_section_b 实际读的是 A）

```c
std_render_section_b(ctx, mask)
{
    ptr = ctx->offset_a;                 // param_1[299]

    while (*(short*)ptr >= 0) {          // 索引 < 0 表示结束
        entry = ctx->obj_ptrs[*(short*)ptr];
        if (entry->type == mask) {       // +2 处类型

            // 世界坐标 = 对象基准 + 区段记录坐标 - 相机位置
            pos.x = entry->x + ptr[1] - camx;
            pos.y = entry->y + ptr[2] - camy;
            pos.z = entry->z + ptr[3] - camz;

            if (dist2 <= 1.69e6) {       // 1300^2 距离剔除
                depth = pos · view_dir;
                if (depth >= 60.0 && depth <= 880.0) {
                    entry->flags |= 2;   // 可见
                    // 绘制子对象
                }
            }
        }
        ptr += 16;                       // 下一条记录
    }
}
```

### 3.4 关键数值

| 参数 | 值 |
|------|-----|
| 记录大小 | **16 字节** |
| 距离剔除平方 | **1.69e6**（1300²） |
| 近裁剪 | **60.0** |
| 远裁剪 | **880.0** |

### 3.5 各区段的最终归属

| 区段 | 内容 | 消费者 |
|------|------|--------|
| 文件头 | 计数 + 偏移 | `std_load_stage` |
| `+0x490` 指针表 | 对象指针 | `std_render_section_b` |
| **区段 A** | **16 字节放置记录** | **`std_render_section_b`** |
| 区段 B | **指令流（0x14 字节）** | ⬜ 未找到消费者 |

## 6. 区段 B 的结构（第 35 轮补充）

虽然仍未找到消费者，但结构已解出。

### 6.1 实测数据

```
stage1.std 区段 B: 0xaac 起，820 字节
前 40 字节: 00 00 00 00 09 00 0c 00 00 00 00 00 00 00 80 3f
            00 00 00 00 00 00 00 00 0b 00 0c 00 92 0a 06 3f
            00 00 00 00 00 00 00 00
```

### 6.2 两种解读的对照

| 解读方式 | 结果 | 判断 |
|---------|------|------|
| **0x14 字节指令** | `time=0, op=9, args=(0,0,0)` | ✅ 数值合理 |
| 16 字节记录 | 索引 0，浮点 `1.1e-39` | ❌ 荒谬 |
| 纯 float 三元组 | `(0,0,1.0)`、`(0.524,0,0)` | 🔶 部分合理 |

**结论：区段 B 是 `0x14`（20）字节的指令流**，与摄像机 VM 的指令大小相同。

### 6.3 字段推测

```
+0x00  i32   ?（恒为 0）
+0x04  i16   op   （取值 9, 11...）
+0x06  i16   type （恒为 0x000c）
+0x08  float ×3
```

其中 `0x0c` 类型码与第 6 轮从原始字节看到的 `(?, 0x000c)` 指令对**完全一致**。

### 6.4 与摄像机 VM 的巧合

| 结构 | 指令大小 | op 取值范围 |
|------|---------|------------|
| **摄像机 VM** (`cam_run_script`) | 0x14 | 0..10 |
| **`.std` 区段 B** | 0x14 | 9, 11... |

**两者大小相同但内容不同**，容易混淆。区段 B 的 op 出现 11，
而摄像机 VM 只定义到 10，说明**它们不是同一套指令集**。
