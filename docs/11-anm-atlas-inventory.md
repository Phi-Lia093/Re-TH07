## 1. UV 是怎么算的（已完全解出）

### 1.1 渲染器读 UV 的代码

```c
// FUN_0044efb0(anim, spritePtr, flags)
_DAT_004b9fbc = *(float *)(*(int *)(sprite + 0x1e4) + 0x1c) + *(float *)(sprite + 0x28);
_DAT_004b9fd8 = *(float *)(*(int *)(sprite + 0x1e4) + 0x24) + *(float *)(sprite + 0x28);
_DAT_004b9fc0 = *(float *)(*(int *)(sprite + 0x1e4) + 0x20) + *(float *)(sprite + 0x2c);
_DAT_004b9ff8 = *(float *)(*(int *)(sprite + 0x1e4) + 0x28) + *(float *)(sprite + 0x2c);
```

### 1.2 字段对应

`sprite_t` 结构（20 字节）：

```c
struct Sprite {
    u32   id;      // +0x00
    float x, y;    // +0x04, +0x08
    float w, h;    // +0x0C, +0x10
};
```

渲染器对 sprite 指针做 `+0x1c / +0x20 / +0x24 / +0x28` 位移，
而 `0x1c` 相对结构起点恰好是 **`x`、`y`、`w`、`h`** 的偏移
（结构前面还有 0x1c 字节的头，指向实际的 x 字段）。

因此四个角被固定为：

```
u0 = x,      v0 = y
u1 = x + w,  v1 = y + h
```

**UV 归一化**：

```python
u0_norm = x / atlas_w
v0_norm = y / atlas_h
u1_norm = (x + w) / atlas_w
v1_norm = (y + h) / atlas_h
```

### 1.3 实例

`ascii.anm` 里字形 `'A'`（id=65）：

```
x=32, y=64, w=16, h=16   (atlas 256×256)
UV = (0.1250, 0.2500) .. (0.1875, 0.3125)
```

## 2. 纯色 3D 顶点（28 字节）

精灵批次最终通过以下调用提交：

```c
// FUN_0044f5c0 —— 批次 flush
DrawPrimitiveUP(
    D3DPT_TRIANGLESTRIP,
    count << 1,        // 顶点数
    vertexBuffer,
    0x1c);             // 28 字节/顶点

// FUN_0044f690 —— 顶点填充，每个顶点 7 个 dword
```

**28 字节 = 7 × float**，字段顺序（由填充逻辑推断）：

| 偏移 | 字段 |
|------|------|
| +0x00..0x08 | x, y, z |
| +0x0C..0x14 | u, v（?） |
| +0x18 | 颜色/标志 |

> 注：另一处绘制路径（加载进度条）用的是 20 字节顶点
> （`x,y,z,u,v`），说明**存在两套顶点格式**：
> 28 字节用于通用精灵批次，20 字节用于简单四边形。

## 3. 字体：`ascii.anm`（**HUD 的核心**）

### 3.1 结构

```
entry0: atlas 256×256 ARGB4444, 146 sprites
entry1: 同上布局，配色不同（蓝 vs 橙主题）
```

### 3.2 **sprite id == ASCII 码**（关键机制）

16×16 的字形精灵构成标准字符网格，编号 **31..128**，且：

```
id 0x21 ('!') .. 0x7F
```

**要显示字符 `c`，就画 `sprite[ord(c)]`。**

这解释了 HUD 的文字渲染：**逐字符按 ASCII 码索引 sprite**。

### 3.3 字形网格

```
id=31 @(0,32)    每格 16×16
id=47 @(0,48)    每行 16 个
id=63 @(0,64)
```
即 `col = x/16`，`row = y/16`，`id ≈ 32 + (row-2)*16 + col`

### 3.4 其他尺寸的 sprite

| 尺寸 | 数量 | 用途 |
|------|------|------|
| 16×16 | 98 | **ASCII 字形** |
| 8×8 | 30 | **HUD 小图标**（残机/Bomb 标记等） |
| 8×12 | 10 | 细长字符（`!`、`:` 等） |
| 256×32 | 2 | 长条（`東方妖々夢` logo） |
| 48×16 | 2 | |
| 48×8 | 1 | |

### 5.5 每项两行：选中态是 v+64（已验证）

每个菜单项在 sprite 表里占 **两格**：宽高相同，**v 坐标精确相差 64**：

```
id= 0  uv=(  0,  0)  80×32      ← 普通态
id= 1  uv=(  0, 64)  80×32      ← 选中态
id= 2  uv=( 80,  0) 160×32
id= 3  uv=( 80, 64) 160×32
id= 4  uv=(240,  0) 192×32
id= 5  uv=(240, 64) 192×32
id= 6  uv=(  0, 32)  96×32
id= 7  uv=(  0, 96)  96×32      ← 32+64
id= 8  uv=( 96, 32)  96×32
id= 9  uv=( 96, 96)  96×32
```

规律：
```
选中态 sprite 的 (x, y, w, h) = (普通态.x, 普通态.y + 64, w, h)
```

图集按 **v 分层**：
- `v = 0..31`    第 1 行普通态
- `v = 32..63`   第 2 行普通态
- `v = 64..95`   第 1 行选中态
- `v = 96..127`  第 2 行选中态
- `v = 128..191` 第 3 行普通态
- `v = 192..255` 第 3 行选中态

> **重制要点**：只需把选中态调到 v+64 即可复刻高亮效果，
> 不需要额外做高亮渲染。

## 7. 对重制的意义

### 7.1 高清化的最小改动路径

因为 **UV 是归一化的**，替换贴图时：

```
新图集 512×512（原 256×256）
sprite 的 x,y,w,h 全部 × 2
UV 公式不变 → 归一化坐标完全一致
```

**渲染代码一行都不用改。**

### 7.2 各资源的高清化优先级

| 优先级 | 资源 | 理由 |
|--------|------|------|
| 1 | `ascii` | HUD 全部文字，最常看 |
| 2 | `etama` | 弹幕视觉 |
| 3 | `player00-02` | 自机 |
| 4 | `title01`/`result00` | 界面 |
| 5 | `eff*` | 特效 |
| 6 | `stg*bg` | 背景 |

### 7.3 菜单文字的特殊处理

`title01` e1 的 94 项文字可以：

- **方案 A**：沿用贴图（保持原样）
- **方案 B**：改用系统字体渲染（更清晰，但需精确匹配原布局）

建议 A，因为文字图集本身就带艺术风格，且布局已是精确的图集切分。
