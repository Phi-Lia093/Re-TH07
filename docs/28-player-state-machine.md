## 2. 决定性证据：碰撞检测

`FUN_0043e4e0` 是全字段引用最多的函数，其逻辑为：

```c
if (state == 0 || state == 3 || state == 4) {
    // 矩形相交测试
    if (box.right < this->x_min ||
        this->x_max < box.left  ||
        box.bottom < this->y_min ||
        this->y_max < box.top) {
        return 0;      // 不碰撞
    }
    return 1;          // 碰撞
}
return 0;              // 状态 1、2：永远不碰撞
```

**关键**：

| 状态 | 碰撞判定 |
|------|---------|
| 0 | 有 |
| **1** | **无（无敌）** |
| **2** | **无（无敌）** |
| 3 | 有 |
| 4 | 有 |

### 2.1 铁证：唯一调用者是子弹系统

```
FUN_0043e4e0 的唯一调用者 = bullet_update_all（FUN_00432990）
```

**这是一个「子弹 vs 玩家」的碰撞检测函数。**

所以「状态 1、2 返回 0」的含义是明确的：
**子弹打不到玩家** —— 这就是无敌。

没有任何歧义空间。

## 3. 状态语义推导

结合：

1. Bomb 序列把状态从默认推向 `1` → `4`
2. 状态 1、2 无碰撞
3. 状态 1、2 会抑制射击计时器（`player_shoot_timer`）
4. 状态 3 被赋值 15 次（最常态）

得出：

| 状态 | 含义 | 判定 | 可射击 |
|------|------|------|--------|
| **0** | 正常（初始） | ✅ | ✅ |
| **1** | **Bomb 启动 / 无敌** | ❌ | ❌ |
| **2** | **Bomb 进行中 / 无敌** | ❌ | ❌ |
| **3** | **正常（战斗中）** | ✅ | ✅ |
| **4** | Bomb 收尾 | ✅ | ✅ |

> 状态 0 与 3 都是"正常"，区别可能是初始化阶段与正常游玩。
> 状态 4 已恢复判定，说明无敌在收尾前结束。

## 4. 状态转移

```c
// Bomb 结束 / 进入战斗
player->state = 3;          // 15 处写入，最常见

// Bomb 启动
player->state = 1;          // 2 处

// Bomb 进行
player->state = 2;          // 1 处

// Bomb 收尾
player->state = 4;          // 1 处

// 初始化
player->state = 0;          // 1 处
```

### 4.1 Bomb 流程中的转换

```
0 (空闲)
 └─ 按 Bomb 键 → 1 (启动，无敌开始)
     └─ 计时 → 2 (进行，无敌)
         └─ 生效 → 3 (恢复判定)
             └─ 收尾 → 4 → 3
```

---

## 5. 无敌与判定的关系（重要）

**无敌不是独立计时器，而是由状态字段间接实现的**：

```c
// 碰撞函数
if (state == 1 || state == 2) return 0;   // 无碰撞
```

重制版如果实现「无敌计时器 + 碰撞时跳过」，效果等价，
但要注意状态 4 已经恢复判定 —— **无敌在 Bomb 特效完全结束前就结束了**。

## 7. 方法论记录

这一节记录**如何避免再犯上一轮的错误**：

### 7.1 错误模式

只看单个函数的表现特征（隐藏精灵、生成特效、多阶段）
就推断语义 —— 这些特征在死亡和 Bomb 中都成立。

### 7.2 正确方法

**先交叉引用状态字段的所有读写点**：

```powershell
python tools/field_xref.py 0x2408
python tools/field_xref.py 0x2408 --writes-only
```

一个字段在 27 个函数中的用法，比单个函数的表现可靠得多。

### 7.3 具体判据

本例中真正的判据是**碰撞函数对状态的过滤** ——
只有 Bomb 才会让碰撞失效，死亡不会。
