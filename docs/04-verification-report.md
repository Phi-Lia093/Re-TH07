# L3 验证器报告 — 原版 ECL 行为自洽性

> 目的：在**无法运行游戏**的前提下，验证我们对 ECL 的理解是否正确。
> 方法：把语义模型写成可执行模拟器，跑完全部真实指令，统计任何不可能的状态。
>
> **结论：762 个子程序、260 万次指令执行，零异常。**
> 且验证器本身通过 5/5 注入缺陷自测 —— 它确实能抓错，不是"永远通过"。

---

## 1. 验证器检查什么

| 检查项 | 触发条件 | 含义 |
|--------|---------|------|
| `unknown-opcode` | opcode 不在签名表 | 语义表缺口 |
| `size-mismatch` | `size-12` 的槽数与签名不符 | 参数布局理解错误 |
| `bad-ip` | 跳转落在任何指令/哨兵之外 | 偏移语义错误 |
| `bad-call-target` | `ins_41` 目标 ≥ 子程序数 | 子程序号理解错误 |
| `stack-overflow` | 调用深度 ≥ 16 | 与引擎硬限制冲突 |
| `budget` | 单实例执行超 20 万步 | 无法终止 |
| `bad-var` | 掩码位声明是变量但值非法 | 掩码语义错误 |

## 3. 自测（证明验证器有效）

`python tools/verify_selftest.py` 向真实数据注入缺陷：

```
[PASS] clean file must report nothing               clean
[PASS] unknown opcode 0xFF                          unknown-opcode
[PASS] instruction size vs signature                size-mismatch
[PASS] call target out of range                     bad-call-target
[PASS] misaligned jump target                       bad-ip
5/5 self-tests passed
```

**这一步是必须的**：一个只会输出"无异常"的验证器毫无价值。
注入缺陷后能被抓到，才说明"零异常"是真实结论。

## 4. 过程中的发现（重要，均来自异常诊断）

调试过程中出现了多轮误报，每一轮都逼出一个**真实的语义认识**：

### 4.1 `ins_3` 的计数器是普通 ECL 变量

最初把它当成「按操作数自增的私有计数器」，结果所有循环永不终止。
真实语义：

```c
var -= 1;                       // 变量就在 ECL 变量区
if (var >= 1) { time = t; ip += cp; }
```

而 `ins_4` 可以在循环体内**重新赋值同一个变量**（Sub108 的
`0xae30 ins_4(10012, 4)`），这正是"每 N 次做一次某事"的写法。

### 4.2 `ins_2` 的「时间回绕」是正常协程

`Sub26` 的典型形态：

```
0x32e8 call sub25
0x3318 call sub22
0x3328 call sub21
0x3358 call sub23
0x3368 call sub24
0x3398 ins_2(t=120, cp=-176)   <- 跳回 0x32e8
```

这是**每 120 帧轮询一次**的定时器，不是死循环。
验证器按「向后跳转」而非「时间回退」识别它 —— 因为 `t=120` 是时间前进。

### 4.3 条件跳转必须真的求值

`ins_32(10016, 2, 0, 112)` = 「如果难度 < 2 则跳过本段」。
最初无条件执行跳转，导致受保护段落无限重跑。

### 4.4 参数格式的四种反编译形态

生成签名表时发现，反编译对参数的表达远不止一种：

| 形态 | 例子 | 识别方式 |
|------|------|---------|
| 掩码读取 | `if (mask & 2) ... local_c[4]` | 位序即槽序 |
| 低字节读取 | `(*(byte *)(local_c + 3) & 1)` | 槽 3 的 bit0 |
| 整体委托 | `FUN_0040f8f0(param_1, ...)` | 被调函数内读 `instr+0x14` |
| 指针别名 | `local_1c = local_c + 3; ... local_1c[5]` | 槽 3+5 = 8 |

**141 个 opcode 中，112 个由「反汇编槽数」与「真实字节」双向印证**，
其余 29 个以数据为准（数据由 `thecl` 与全部 8 个关卡文件共同确定，
比单一反编译路径可靠）。

## 5. 这份报告**不能**证明什么

必须明确边界，避免过度自信：

| 能证明 | 不能证明 |
|--------|---------|
| 参数槽数与真实字节一致 | 参数的**含义**正确（角度 vs 速度） |
| 跳转偏移基准正确 | 比较运算的方向正确（`<` vs `<=`） |
| 调用/返回结构正确 | 运动、弹幕的**数值**正确 |
| 无越界、无递归爆栈 | 视觉效果与手感 |

**也就是说：L3 能证明"结构没错"，不能证明"数值对"。**

数值正确性仍需人工对照，或最后拿原版录像对比。

## 6. 复现

```powershell
python tools/verify_ecl.py

python tools/verify_ecl.py --start-sub 5   # 只跑某个子程序

# 证明验证器有效
python tools/verify_selftest.py
```
