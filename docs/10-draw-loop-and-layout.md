> 状态：**绘制管线已解出**；界面布局部分解出。
> 目标：为「高分辨率等比例缩放」提供准确依据。

## 1. 结论先行：ANM 有没有动画和 UV？

**两者都有，而且是完整的动画系统。**

| 问题 | 答案 | 证据 |
|------|------|------|
| ANM 有动画吗？ | **有**，完整时间轴动画 | `player00` 有 35 个脚本、357 条指令 |
| ANM 有 UV 吗？ | **有**，但 UV 来自 **sprite 表**，不是逐帧存像素坐标 | 见 §3 |
| 动画如何描述？ | 字节码指令流：`(时间, 操作码, 参数)` | 39 个 opcode 全部验证 |

### 1.1 典型动画脚本（灵梦走路，script 1）

```
t=0   set_sprite(sprite 4)      ← 切换图集矩形
t=3   set_sprite(sprite 5)
t=6   set_sprite(sprite 6)
t=14  set_sprite(sprite 7)
t=22  set_sprite(sprite 8)
t=30  set_sprite(sprite 9)
t=38  set_sprite(sprite 10)
t=46  loop 回 t=0                ← 循环
```

**这就是"动画"的本质**：按时间轴切换 sprite 索引，而每个 sprite 携带一个
UV 矩形（来自图集切分）。

## 2. ANM 指令集（39 个 opcode，格式全部验证）

### 2.1 指令头

```c
struct AnmInstr {          // 8 字节
    u16 type;              // opcode
    u16 length;            // 本指令总字节数
    i16 time;              // 生效帧
    u16 param_mask;        // ECL 风格参数掩码
    /* 参数，紧跟其后 */
};
```

### 2.2 参数类型与大小（**关键发现**）

来自 thtk `formats_v2`（TH07 = version 2），并用**真实数据长度**验证：

| 格式符 | 含义 | **大小** |
|--------|------|---------|
| `n` | 浮点（float） | 4 |
| `f` | 浮点（float） | 4 |
| `S` | **整数** | **4**（不是 2！） |
| `o` | 偏移 | 4 |
| `t` | 时间 | 4 |

> **`S` 在 ANM 中是 4 字节**。这是个容易踩的坑：
> 若按 int16 处理，21 个 opcode 的长度会算错。
> 按 4 字节处理后，**39/39 个 opcode 的数据长度与实测完全一致**。

### 2.3 验证结果

对全部 63 个 ANM 文件的**所有脚本指令**统计实际参数长度，与格式表对照：

```
op  fmt      预测  实测  结果
 0            0     0  OK
 3  n          4     4  OK
 5  Sot       12    12  OK
32  SSfff     20    20  OK
...

42 个 opcode 全部 OK，0 个 MISMATCH
5 个 opcode 无格式条目：59, 60, 69, 79, 80
```

**说明**：thtk 的 `formats_v2` 表不覆盖 TH07 实际使用的全部 opcode。
剩下 5 个（长度 8/8/16/4/4 字节）是**扩展指令**，
长度合法但没有权威格式定义，需从反汇编补。

|----|---------|------|---------|

### 2.5 又一个「相对偏移」陷阱

修正了一处会导致脚本解析彻底错位的问题：

**`nextoffset` 链上的条目，其 `script_offsets` 也是相对条目头部的。**

实测 `etama.anm` 条目 1（头部在 `0x21644`），脚本 0 的偏移字段为 `0x640`：

| 读法 | 结果 |
|------|------|
| 当作绝对偏移 @`0x640` | `type=0 len=16768 pm=0x4180` ← **垃圾** |
| 加上条目基址 @`0x21c84` | `type=3 len=12 pm=0` ← **合法的 set_sprite** |

这与 sprite 表是**同一个坑**。修正后，
超出格式表的 opcode 从 11 个降到 5 个。

> 规律：**entry 0 的偏移是绝对的**（base=0 时两者等价），
> **entry 1+ 的偏移是相对的**。统一用 `base + off` 即可两种情况都对。

## 3. UV 从哪里来

**Sprite 表提供 UV，而不是每条动画指令**：

```
[AnmHeader]
  sprite_offsets[]  ──>  sprite_t { id, x, y, w, h }   ← UV 矩形在这里
  script_offsets[]  ──>  动画指令流
```

`set_sprite(n)` 只是**选一个索引**，真正的 UV 由 `sprite[n]` 的
`(x, y, w, h)` 决定。

> **重制的意义**：高清化只需**替换 THTX 像素**并**等比放大
> sprite 的 w/h**，UV 的归一化坐标可以完全复用 —— 这是布局能够
> 1:1 保留的数学基础。

## 4. 绘制循环（已解出）

### 4.1 顶点格式

```c
struct Vertex {     // 20 字节
    float x, y, z;  // 0x00..0x0B  3D 位置
    float u, v;     // 0x0C..0x13  UV
};
```

**没有顶点色**。这与之前对「MODULATE 着色」的推断**冲突**——
着色可能通过 `D3DCOLOR` 纹理阶段常量或设置 `TextureFactor` 实现，
需要进一步确认。

### 4.2 绘制调用

```c
SetVertexShader(0x44);                    // FVF
DrawPrimitiveUP(
    primType = 5,     // D3DPT_TRIANGLESTRIP
    count    = 2,     // 2 个三角形 = 1 个四边形
    vertices = quad,  // 4 个顶点
    stride   = 0x14); // 20 字节
```

**每个精灵 = 1 次 `DrawPrimitiveUP`，4 顶点三角带。**

> 这是最容易优化的地方：TH07 每帧数千次独立绘制调用。
> 重制版应**合批（batching）**：同贴图的四边形合并为一个 VBO，
> 可把数千次调用降到个位数。**这不会改变画面，只提升性能。**

### 4.3 绘制流程

```
1. AnmManager 解析动画脚本 → 得到 (spriteId, x, y, z, scale, alpha, ...)
2. 查 sprite[spriteId] → UV 矩形 (u0,v0,u1,v1)
3. 按 (x,y,z) 与缩放构造 4 顶点
4. SetTexture(stage0, atlas)
5. SetTransform(projection/view) 已有
6. DrawPrimitiveUP → 绘制
```

### 4.4 纹理阶段设置（每次绘制前）

```c
SetTextureStageState(0, D3DTSS_MAGFILTER, D3DTEXF_LINEAR);   // (0,4,2)
SetTextureStageState(0, D3DTSS_MINFILTER, D3DTEXF_LINEAR);   // (0,1,2)
SetTextureStageState(0, D3DTSS_MIPFILTER, D3DTEXF_NONE);     // (0,5,0)
SetTextureStageState(0, D3DTSS_COLOROP,   D3DTOP_SELECTARG1);// (0,2,0)
SetTextureStageState(0, D3DTSS_COLOROP,   D3DTOP_MODULATE);  // (0,1,4) 另一套
```

### 4.5 层序（z 值）

所有精灵共享一个透视相机（`fov = π/10`），**靠 z 值分层**：

| 层 | z 范围（推断） | 内容 |
|----|--------------|------|
| 远景背景 | 大（数百~数千） | `stgNbg.anm` |
| 中景 | 中 | 背景视差层 |
| 游戏对象 | z ≈ 5~20 | 敌人、子弹、自机 |
| 前景特效 | 小 | 特效、闪光 |
| **UI/HUD** | **最小（最靠近相机）** | 分数、残机、文字 |

> 这也解释了为什么 UI 不会被子弹遮挡：**UI 的 z 最靠近相机**。

### 5.4 已解出的一个具体 UI：读盘进度条

`FUN_0042a876` 绘制加载进度：

```c
// 进度 0 → 48 像素
if (frames < 60)
    bar_h = ((frames + frac) * 48.0) / 60.0;
else
    bar_h = 48.0;

// 顶点（三角带，4 个）
v0 = (SCR_W + 16,              384.0,            0, u?, 1.0)
v1 = (SCR_W + 384 - 16,        384.0 + bar_h,    0, ...)
v2 = (SCR_W + 16,              384.0 + bar_h,    0, ...)
v3 = (SCR_W + 384 - 16,        384.0,            0, ...)
```

其中 `SCR_W = DAT_0062f864` 是屏幕宽度变量。
**进度条在固定坐标绘制，长度 48px 随时间线性增长。**

> 这是一个**可直接复用的 UI 布局样本**：
> 它证明了 UI 元素用**绝对坐标**（`+16`、`-16` 边距，`384` 长度）绘制，
> 且**不受游戏区坐标影响**。

## 6. 高分辨率等比例缩放方案

用户要求：**按原布局等比例缩放，可以留边**。

### 6.1 核心原则

**布局用「逻辑坐标」定义，只在渲染时缩放。**

```lua
-- 逻辑分辨率固定 640×480
LOGICAL_W, LOGICAL_H = 640, 480

-- 等比缩放 + 居中留边
scale    = math.min(screen_w / LOGICAL_W, screen_h / LOGICAL_H)
dst_w    = LOGICAL_W * scale
dst_h    = LOGICAL_H * scale
offset_x = (screen_w - dst_w) / 2
offset_y = (screen_h - dst_h) / 2
```

### 6.2 关键：哪些量必须缩放，哪些绝对**不能**

这是整个方案里最容易出错的地方。

| 类别 | 处理 | 理由 |
|------|------|------|
| UI 位置 / 尺寸 | **× scale** | 布局等比 |
| 精灵贴图 | 高清重制 | |
| 文字字号 | × scale（取整） | 清晰度 |
| **判定点半径** | ❌ **不缩放** | 手感 |
| **移动速度** | ❌ **不缩放** | 手感 |
| **子弹速度 / 判定** | ❌ **不缩放** | 手感 |
| **ECL 逻辑帧** | ❌ **不缩放** | 时序 |

> **一句话**：`scale` 只作用于**绘制**，
> **逻辑更新（位置、速度、判定、时间）一步都不变。**

如果误把速度也乘 scale，弹幕会变快 2 倍，游戏完全无法玩。

### 6.3 留边计算实例

| 分辨率 | scale | 画布尺寸 | 留边 |
|--------|-------|---------|------|
| 1280×960 | 2.0 | 1280×960 | 无（完美 2 倍） |
| 1920×1080 | 2.25 | 1440×1080 | 左右各 240 |
| 2560×1440 | 3.0 | 1920×1440 | 左右各 320 |
| 3840×2160 | 4.5 | 2880×2160 | 左右各 480 |

### 6.4 推荐的两阶段实现

**阶段一：整体等比（先保证正确）**

- 渲染到 640×480 的逻辑画布
- 整体放大到窗口
- **布局 100% 保真，可直接与原版对照**
- 缺点：贴图被放大，有模糊

**阶段二：高清资源（逐步替换）**

- 逻辑坐标乘 scale
- 逐张把 THTX 贴图换成高清版本
- 因为 UV 是归一化的，**布局数学完全不变**
- 这是 ANM 结构带来的最大好处

### 6.5 HUD 可以优先高清化

HUD 与游戏逻辑**完全解耦**（用绝对坐标、共享 ascii 图集），
所以即使整体还在阶段一，也可以**先单独高清重绘 HUD**，
不影响任何手感。

## 7. `.std` 关卡数据（结构已解出）

### 7.1 文件布局

```c
struct StdHeader {         // 16 字节
    u16 unknown;
    u16 count;
    u32 offsetA;           // 区段 A 起点
    u32 offsetB;           // 区段 A 终点 / 区段 B 起点
};
// [区段 A]  16 字节定长记录数组，以 0xffffffff 终止
// [区段 B]  第二块数据（具体结构未完全解出）
```

### 7.2 区段 A：对象放置记录（16 字节）

```c
struct StdRecord {
    u16 tag;      // 0x0000 / 0x0001 交替出现
    u16 pad;
    float f0, f1, f2;
};
```

**实测 8 个关卡**：

| 文件 | 记录数 | 区段 B 大小 | f0 范围 | f1 范围 |
|------|-------|-----------|---------|---------|
| stage1 | 59 | 820 | -192..320 | **-56..6600** |
| stage2 | 76 | 720 | -256..-64 | **-56..5576** |
| stage3 | 92 | 860 | -672..-192 | **-264..11000** |
| stage4 | 157 | 1800 | -180..180 | **-180..11000** |
| stage5 | 162 | 800 | -128..0 | **-100..9088** |
| stage6 | 36 | 1200 | -128..-128 | **-200..4152** |
| stage7 | 162 | 840 | -128..0 | **-100..9088** |
| stage8 | 162 | 840 | -128..0 | **-100..9088** |

**关键观察**：

1. **`f1` 是关卡纵深坐标**，范围从负值延伸到 4000~11000
   —— 这正是关卡向前推进的距离。
2. `stage7` 与 `stage8` 的记录**完全相同**（162 条、f0/f1 范围一致），
   印证 Extra/Phantasm 共用地图。
3. `stage1` 的 `f1` 值以 **256 为步长**递减（6600, 6344, 6088, 5832...），
   `f0` 恒为 -192 —— 这是沿关卡布置的**对象列**。

### 7.3 区段 B

包含大量 `ffffffff` 分隔符和 `(? , 0x000c)` 形式的指令对，
结构与 ANM 脚本类似但尚未解出。

> `.std` 属于**关卡层**（背景几何、对象布局），
> 不影响 2D 精灵绘制。3D 背景的主体来自 `stgNbg.anm` +
> 独立相机（见 `docs/09-rendering-d3d8.md` §3.4）。
