# TH07 重制：弹幕 STG 引擎框架 设计计划

> **定位**：一个通用的弹幕 STG 游戏框架，妖妖梦作为第一个内容包。
> **原则**：纯重写、拒绝古代二进制、现代可读配置、可移植。
> **技术**：C++20 + OpenGL 3.3 Core + Lua。

---

| 优先级 | 目标 | 说明 |
|--------|------|------|
| **P0** | 玩法正确 | 手感、判定、计分与 TH07 一致 |

## 2. 核心架构决策

### 2.1 分层

```
┌─────────────────────────────────────────┐
│  Content Pack (th07)      Lua + 数据    │  ← 妖妖梦特殊内容全在这层
├─────────────────────────────────────────┤
│  Game Framework                         │  ← 通用：VM、实体、渲染管线
├─────────────────────────────────────────┤
│  Platform Layer                         │  ← SDL3 + GL330 + 音频
└─────────────────────────────────────────┘
```

**关键**：框架层**不含任何妖妖梦专有名词**。所有"妖妖梦特有"的东西
（Bomb 行为、樱点、灵梦/魔理沙/咲夜的 SHT）都在内容包里。

### 2.2 数据格式全部转换

| 原格式 | 新格式 | 转换方式 |
|--------|--------|---------|
| `.ecl` (12B 指令) | **Lua 脚本** | 离线转译器 + 手写校验 |
| `.anm` (8B 指令) | **TOML 定义 + PNG 图集** | 离线转换 |
| `.std` (16B 记录) | **TOML** | 离线转换 |
| `.sht` (二进制) | **TOML** | 离线转换 |
| `.msg` (12B 指令) | **Lua 对话脚本** | 离线转译 |
| `.rpy` (录像) | **TOML/JSON** | 新设计 |
| THTX/JPG | **PNG** | 转换 |
| MIDI | **OGG/Opus** | 预渲染或保留 MIDI |
| WAV | **OGG/Opus** | 转换 |

> **拒绝二进制**：运行时**不解析任何原版格式**。转换在构建期完成。

### 2.3 Lua 的角色

**Lua 是内容层的脚本语言，不是引擎实现语言。**

| 层 | 语言 |
|----|------|
| 平台层 | C++ |
| 框架层（VM、实体、渲染） | C++ |
| **内容层（敌机行为、弹幕模式）** | **Lua** |
| **配置（关卡、自机、UI）** | **TOML** |

**Lua 里可以直接写运算表达式**，不需要 `add`/`fadd` 这类函数调用：

```lua
-- 好：直接算符
local speed = base_speed * (1 + difficulty * 0.15)
local angle = math.atan(dy, dx) + spread

-- 坏（这正是原版 ECL 的做法，要避免）
local speed = fadd(fmul(base_speed, fadd(1, fmul(difficulty, 0.15))))
```

## 4. 关键技术方案

### 4.1 ECL → Lua 转译

**这是工作量最大也最关键的转换。**

原版 ECL 是「时间轴 + 指令 + 参数」的格式。转译目标：

```lua
-- 原 ECL: time=0, op=ins_21(wait), arg=30
-- 转译后:
wait(30)

-- 原 ECL: time=60, op=ins_97(fire), args=(10, 5, 0x1234)
-- 转译后:
fire_ring{
  count  = 10,
  speed  = 5.0,
  angle  = 0x1234 / 65536 * math.pi * 2,
}
```

**转译策略**：
1. **保留时间轴结构**（`wait()` 表达延迟）
2. **运算直接展开**（不保留 `fadd`/`fmul` 函数调用）
3. **保留变量语义**（ECL 变量 → Lua 局部变量 + 显式作用域）

### 4.1.1 真实规模（实测）

| 项 | 数值 |
|----|------|
| ECL 指令总数 | **19,919** |
| 实际使用的 opcode | **141**（不是全部 161） |
| 最频繁的 opcode | `op4`（12.8%）、`op5`（11.4%） |

**覆盖曲线很平缓**：

```
前 8 个 opcode   → 41.8%
前 12 个         → 49.5%
前 28 个         → 70.0%
全部 141 个      → 100%
```

**这意味着不能靠"先做几个高频 opcode"来快速出效果** ——
没有少数几个占绝对多数的情况，必须系统性处理全部 141 个。

**风险**：141 个 opcode 的语义映射需要逐个验证。
**缓解**：
- 按 opcode 分组实现（数据操作类、弹幕生成类、控制流类）
- 每组完成后用原版 ECL 数据跑对照测试
- `docs/03` 已有完整语义表，实现是"照着写"而非"重新推断"

### 4.2 渲染：双相机 + 精灵批处理

```cpp
// 已知：主投影 fov = π/10，背景相机 fov = π/6
struct Camera {
    float fov;       // π/10 主，π/6 背景
    float near = 1.0f;
    float far  = 10000.0f;
    Vec3  up   = {0, -1, 0};   // Y 轴向下
};

// 游戏区：局部坐标 (0,0) 起，绘制时 + (32,16)
constexpr Vec2 kPlayfieldOrigin = {32.0f, 16.0f};
constexpr Vec2 kPlayfieldSize   = {384.0f, 448.0f};
```

**精灵批处理**：按 z 分组，同组内一次 draw call。

### 4.4 Lua 与 C++ 的接口

使用 **sol2**。

```cpp
// 框架暴露给 Lua 的 API
lua["spawn_bullet"] = [](BulletDesc d) { world.spawn(d); };
lua["wait"]         = [](int frames) { co_yield frames; };
lua["player"]       = &player_binding;
lua["difficulty"]   = std::ref(g_difficulty);
```

**协程模型**：Lua 协程 = 敌机行为，`wait(n)` 挂起 n 帧。

## 6. 风险与对策

| 风险 | 影响 | 对策 |
|------|------|------|
| **ECL 转译语义偏差** | 最高 | 用原版数据做对照测试，逐 opcode 验证 |
| 框架抽象过度 | 延迟 | 先写「能跑第 1 关」的垂直切片，再抽象 |
| 内容包与框架边界模糊 | 后期返工 | 强制审查：框架层禁止出现 th07 字样 |
| 渲染性能 | 中 | 精灵批处理 + 图集，目标 60fps@1080p |
| 音频格式转换 | 低 | 先保留 WAV，后期换 OGG |

## 9. 需要确认的开放问题

1. **ECL 转译的粒度**：逐指令转译成 Lua 函数调用，还是聚合成高层 API（如 `fire_ring`）？
   - 前者保真但有 19,919 条指令的 Lua 代码
   - 后者精简但需手工归纳每个 opcode 的意图

2. **图集策略**：保持 TH07 原始图集，还是重新打包？
   - 原始：保真，但纹理尺寸可能不符合 GL330 最优
   - 重打包：更好，但需验证 UV 无偏移

3. **是否保留录像兼容**：新录像格式 or 尝试兼容 `.rpy`？

4. **自机数量**：先做灵梦一个，还是三个一起？
